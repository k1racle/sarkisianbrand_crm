# Управление промокодами

Parent импортирует `PromotionsModule` в `AppModule`. Схема `PromoCode`/`PromoRedemption`, общие модули, расчёт скидки и frontend этим блоком не изменяются. `PromotionsModule` импортирует существующие `AuthModule`/`PrismaModule`, экспортирует `PromotionsService`.

## Доступ

Все маршруты требуют Bearer JWT и `RolesGuard`. Разрешённые роли: `ADMIN`, `CONTENT_MANAGER`, `MANAGER_SALES`, `SUPERVISOR`. Клиенты B2C/B2B, кладовщики и остальные роли не имеют доступа, включая генерацию и просмотр списка. Публичное применение/расчёт промокода реализуется отдельно parent в checkout.

## Маршруты

Префикс API — `/api/v1/promotions`.

- `GET /` — список `{items, total, page, limit}`. Query: `search` до 160 символов; `status=all|active|inactive|scheduled|expired`; `page=1..100000`, `limit=1..100` (по умолчанию 1 и 50). Поиск по коду/названию, стабильная сортировка: дата создания убывает, код возрастает. Список/количество/статистика читаются в RepeatableRead-транзакции.
- `POST /generate` — тело `{prefix?, length?}` (можно `{}`). Возвращает только `{code}`. Не сохраняет и не резервирует код. По умолчанию `SB-` и 8 случайных символов. Префикс 1–12 ASCII букв/цифр, случайная часть 6–20 символов без легко путаемых I/L/O/0. Используется `crypto.randomInt`, без modulo bias и `Math.random`. Проверяет доступность; коллизии — максимум 10 попыток. Между генерацией и созданием код теоретически может быть занят: POST create проверяет уникальность снова.
- `POST /` — создание. `code` можно не передавать для автоматической генерации. Заданный код нормализуется trim/uppercase, 3–40 символов: первая ASCII буква/цифра, далее ASCII буквы/цифры/дефисы/подчёркивания. Дубликат вручную заданного кода — 409; случайная коллизия авто-кода повторяется максимум 10 раз.
- `PATCH /:code` — частичное редактирование. Обязателен `revision` из последнего ответа; хотя бы одно изменяемое поле тоже обязательно. Сам `code` не изменяется и запрещён в теле PATCH. Устаревшая ревизия — 409 с просьбой обновить список. Успешная ревизия увеличивается на 1.
- `DELETE /:code` — физическое удаление с телом `{"confirmation":"ТОЧНЫЙ-КОД"}`. Подтверждение case-sensitive, без автоматического trim: должно в точности совпадать с нормализованным кодом маршрута. Нет истории — `{code, deleted:true}`; любая запись redemption, включая `RELEASED`, — 409 с предложением отключить промокод. История/FK не удаляются каскадом. Отсутствующий код — 404.

## Поля создания/редактирования

```json
{
  "code": "WELCOME10",
  "title": "Приветственная скидка",
  "type": "PERCENT",
  "amount": 10,
  "minimumAmount": 500,
  "maximumDiscount": 1000,
  "usageLimit": 100,
  "perCustomerLimit": 1,
  "isActive": true,
  "startsAt": "2090-01-01T00:00:00Z",
  "endsAt": "2090-02-01T00:00:00Z"
}
```

При создании обязательны `title`, `type`, `amount`. Название trim, 1–160 символов. `type=PERCENT|FIXED` соответствует колонке `discountType`.

- `amount`: JSON **число**, 0.01–100000000, максимум два знака после запятой; процентная скидка дополнительно не больше 100. Денежные значения сохраняются Prisma.Decimal, не floating-point суммами.
- `minimumAmount`: число 0–100000000, default 0, `null` запрещён.
- `maximumDiscount`: положительный денежный cap либо `null` (без cap). Default null.
- `usageLimit`: положительное целое до 2147483647 либо `null` (без общего лимита). Default null.
- `perCustomerLimit`: положительное целое до 2147483647, default 1, `null` запрещён.
- `isActive`: настоящий JSON boolean, default true, `null`/строковый `"false"` запрещены.
- `startsAt`, `endsAt`: ISO 8601 string с часовым поясом (Z или offset) либо `null` для снятия даты. Если обе заданы, окончание строго позже начала. Будущее начало разрешено. Создание включённого истёкшего кода и явное повторное включение истёкшего кода — 400; редактирование/отключение исторической записи разрешены.
- В PATCH отсутствие поля сохраняет прежнее значение; `null` снимает только nullable даты/cap/общий лимит. В PATCH дополнительно обязателен `revision`.

Глобальный ValidationPipe должен быть включён с transform/whitelist/forbidNonWhitelisted (как в проекте). DTO защищают числовые/boolean поля от некорректного приведения типов даже при `enableImplicitConversion:true`; число в строке не принимается вместо JSON числа. Для page/limit в query строковые числа корректно преобразуются.

## Ответ и история

```json
{
  "code": "WELCOME10",
  "title": "Приветственная скидка",
  "type": "PERCENT",
  "amount": "10.00",
  "minimumAmount": "500.00",
  "maximumDiscount": "1000.00",
  "usageLimit": 100,
  "perCustomerLimit": 1,
  "isActive": true,
  "startsAt": null,
  "endsAt": null,
  "revision": 2,
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z",
  "status": "ACTIVE",
  "usage": {"reserved":2,"applied":3,"total":5,"history":9},
  "canDelete": false
}
```

`status=INACTIVE|EXPIRED|SCHEDULED|ACTIVE`, frontend переводит отображение на русский. `isActive` — административный флаг, `status` учитывает и даты. Денежные поля возвращаются **строками с двумя знаками**, чтобы не терять точность; frontend переводит в числа только при заполнении/отправке формы.

`reserved`/`applied` считаются отдельно. `total` — сумма текущих `RESERVED` и `APPLIED`, участвующая в проверке лимита. `history` включает все статусы. `canDelete` только подсказка для UI; сервер повторно проверяет историю под блокировкой.

Ответ не содержит customerHash, email, заказов, персональных данных или отдельных redemption. Для проверки perCustomerLimit сервис внутри транзакции агрегирует максимальное число действующих резервов/применений одного клиента, но хеш наружу не возвращает. В списке нет N+1 чтения клиентов: используется один агрегат для кодов выбранной страницы.

## Конкурентность и безопасное удаление

PATCH и DELETE внутри Prisma transaction сначала выполняют `SELECT code FROM "PromoCode" WHERE code = ... FOR UPDATE` — **тот же row lock, что в OrdersService checkout**. Затем проверяют актуальную запись/ревизию и историю. PATCH дополнительно выполняет compare-and-swap `updateMany({where:{code,revision}, data:{..., revision:{increment:1}}})` с проверкой count=1.

Общий лимит нельзя установить ниже `RESERVED+APPLIED`. Лимит на клиента нельзя установить ниже максимального уже использованного количества одним клиентом, включая резервы. Снятие общего лимита через null разрешено. Уменьшение лимита до ровно использованного числа разрешено, дальнейшие применения блокирует pricing parent.

Отмена заказа освобождает usage для будущего применения, но не удаляет финансовую историю. Для промокода с любой историей используйте `PATCH {revision,isActive:false}`; удалять redemption/order ради удаления кода нельзя. FK P2003 при конкурентном удалении преобразуется в безопасный 409 без метаданных БД.

## Мок-проверки

```powershell
npm.cmd test -- --runInBand promotions
```

Тесты не запускают backend, не используют настоящую БД/заказы, не сохраняют/удаляют реальные промокоды и не вызывают провайдеры. Проверяются нормализация, генерация/коллизии, DTO/типизация, проценты/decimal/cap/даты, статистика без PII, row lock/revision CAS, лимиты по резервам/применениям, подтверждение удаления и сохранение всей истории.

# Очередь почтовых уведомлений

Этот модуль не содержит HTTP-методов просмотра очереди: адреса и содержимое писем не должны попасть в публичный API. Доступ к очереди в будущей админке требует отдельного разрешения и маскирования персональных данных.

## Подключение

Parent регистрирует `NotificationsModule` в `AppModule` и импортирует его в `AuthModule`, где добавляет `PasswordResetRequestController` в `controllers`. Модуль использует глобальный Prisma/Config и собственный stateless-провайдер `IntegrationSecretsService`. Он не импортирует `SystemSettingsModule` или `AuthModule`, поэтому цикла зависимостей нет.

Схема и additive migration `MailOutbox` находятся в ведении parent. Перед компиляцией нужен `prisma generate` после обновления схемы.

```ts
const data = notifications.prepare({
  kind: 'ORDER_CREATED', recipient: customer.email,
  subject: 'Заказ принят', text: 'Содержание письма',
  dedupeKey: `order-created:${order.id}`,
});
await tx.mailOutbox.create({ data }); // в той же транзакции, что и бизнес-событие

// Для независимых уведомлений: повторный вызов с тем же ключом не создаёт новое письмо.
const { id, status } = await notifications.enqueue({
  kind: 'ORDER_CREATED', recipient: customer.email,
  subject: 'Заказ принят', text: 'Содержание письма',
  dedupeKey: `order-created:${order.id}`,
});
```

`prepare` синхронный: возвращает данные `MailOutbox.create`, не читает БД и не отправляет письма. `enqueue` использует upsert без обновления ранее поставленного письма, возвращает только `{id, status}`, а не содержимое. Ключ дедупликации хешируется SHA-256. Не передавайте готовый ciphertext или сырые reset-токены в публичные ответы/логи.

## Безопасный режим и SMTP

Обе переменные по умолчанию **false**. Отсутствие переменной, `false` или `1` не включает отправку. Только явные `true` одновременно разрешают обработку:

```dotenv
MAIL_DELIVERY_ENABLED=false
STOREFRONT_EXTERNAL_CALLS_ENABLED=false

# Настроить на VPS перед отдельной реальной приёмкой, не включать локально.
SMTP_HOST=smtp.example.test
SMTP_PORT=587
SMTP_FROM=sender@example.test
SMTP_USER=sender@example.test
SMTP_PASSWORD=<секрет в окружении>
PUBLIC_APP_URL=https://store.example.test
INTEGRATION_ENCRYPTION_KEY=<случайный секрет минимум 32 символа>
```

В safe mode модуль не запускает таймер, не читает/захватывает очередь и не создаёт SMTP transport. Новые письма могут сохраняться в очереди, но не отправляются. Метод SMTP повторно проверяет оба флага непосредственно перед отправкой. Не выполняется `verify()`, DNS lookup или тестовая отправка при старте.

Шифрование темы и текста — существующий AES-256-GCM `IntegrationSecretsService`. Если `INTEGRATION_ENCRYPTION_KEY` отсутствует, используется `JWT_SECRET`, но подготовка письма требует настроенный секрет минимум 32 символа: известный development fallback запрещён. Секрет нужно сохранять при переездах/восстановлении; без него старые ciphertext нельзя прочитать. Адрес получателя хранится как отдельное поле по согласованной схеме, поэтому резервные копии и доступ к БД тоже должны быть защищены.

Nodemailer настроен по [официальной документации SMTP transport](https://nodemailer.com/smtp): порт 465 использует TLS сразу, остальные требуют STARTTLS; проверка сертификата включена, минимальная версия TLS 1.2. Чтение файлов и URL из сообщений запрещено, SMTP/protocol logging отключён. Отправляется только текст, без внешних картинок и вложений.

## Обработка и восстановление

- Статусы: `QUEUED`, `PROCESSING`, `SENT`, `FAILED`, `CANCELLED`.
- Таймер каждые 10 секунд, до 10 писем последовательно. `processQueue(limit?)` доступен для отдельного будущего воркера; локальное параллельное выполнение исключено.
- Единый SQL `UPDATE ... RETURNING` с `FOR UPDATE SKIP LOCKED` безопасно захватывает одну строку между несколькими процессами. `attempts` увеличивается при захвате; `nextAttemptAt` становится 10-минутной арендой.
- После сбоя процесса строка с истёкшей арендой снова доступна. Финальная истёкшая попытка переводится в `FAILED`.
- Лимит — 5 попыток. Повтор через 1, 2, 4, 8 минут; финальная ошибка переводит письмо в `FAILED`. Ручной перезапуск не реализован, чтобы не позволить обойти лимит через публичный API.
- Завершение/ошибка обновляют только строку со своим `id`, `PROCESSING` и номером попытки. Устаревший воркер не может перезаписать состояние более новой попытки.
- `lastError` содержит только фиксированные русские сообщения. SMTP/Prisma exception, адрес, пароль SMTP, token и текст письма никогда не пишутся в лог.
- Перед отправкой `PASSWORD_RESET` проверяется актуальность токена, активный B2C-владелец и совпадение его текущего email с получателем. Отозванные/просроченные ссылки и письма на уже изменённый адрес переходят в `CANCELLED` без отправки.

Гарантия доставки **at-least-once**, не exactly-once: если SMTP принял письмо, а процесс завершился до фиксации `SENT`, повтор после истечения аренды может отправить его ещё раз. Дедупликация предотвращает повторную постановку бизнес-события, но SMTP не имеет транзакции с PostgreSQL. Реальная приёмка доставки и мониторинг очереди остаются задачей VPS.

## Публичное восстановление пароля

`POST /api/v1/auth/password-reset/request`, тело `{ "email": "client@example.test" }`.

HTTP 202 и одинаковый ответ для существующего/несуществующего адреса, сотрудников, неактивных аккаунтов, cooldown и внутренних ошибок:

```json
{"message":"Если для этого адреса доступно восстановление пароля, мы отправим письмо с инструкциями."}
```

Поиск ограничен `isActive: true`, `role: CUSTOMER_B2C`; B2B и сотрудники используют отдельный административный процесс. Проверка адреса и запрет дополнительных полей выполняются глобальным ValidationPipe. На endpoint назначен `ThrottlerGuard`: 5 запросов с IP за минуту, дополнительно 5-минутный cooldown на адрес по последнему созданному токену. Transaction advisory lock на нормализованный email исключает обход cooldown конкурентными процессами. Небольшая одинаковая минимальная задержка снижает timing enumeration.

Токен — 32 случайных байта, в БД только SHA-256; срок 30 минут. Все неиспользованные токены владельца отзываются в одной транзакции с новым токеном и письмом. Полная ссылка хранится только в зашифрованном тексте письма. Origin берётся из `PUBLIC_APP_URL`, а не заголовков клиента; production требует HTTPS. Этот блок **не меняет** существующий `AuthService.completePasswordReset`: parent должен отдельно проверить атомарное погашение токена/отзыв сессий там.

## Проверки без интеграций

```powershell
npm.cmd test -- --runInBand notifications
```

Все тесты используют моки БД и SMTP; ни один не подключается к PostgreSQL/провайдерам и не меняет клиентов. Проверяются шифрование, оба защитных флага, TLS-настройки, атомарный захват, retry/лимит/аренда, отмена устаревших ссылок, дедупликация, роль B2C, uniform response и cooldown. Отдельно реальный SMTP здесь не проверяется.

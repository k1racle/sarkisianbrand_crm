# Платежи витрины: контракт и безопасный запуск

Реализован серверный REST-клиент ЮKassa. Фиктивные платежи и доверие к присланному статусу удалены. Все проверки в этом блоке выполняются без реальной БД, заказов и провайдеров.

## Ограничение внешних вызовов

`STOREFRONT_EXTERNAL_CALLS_ENABLED=false` — значение по умолчанию при отсутствии переменной. Создание и проверка платежа возвращают HTTP 503 с русским объяснением, HTTP к провайдеру не выполняется. Отключённый режим не читает и не расшифровывает реквизиты. Для включения нужны одновременно значение `true`, включённая интеграция `YOOKASSA`, её реквизиты и корректный `PUBLIC_APP_URL`.

Реквизиты берутся из существующей настройки экосистемы: `config.shopId`, зашифрованный `secretKey` через `IntegrationSecretsService`. Они не возвращаются в API и не попадают в сообщения ошибок. Старое поле `webhookSecret` не используется: уведомления ЮKassa проверяются серверным GET, а не выдуманной подписью. Родителю следует удалить/пояснить это поле в каталоге настроек; этот блок не меняет настройки вне своей зоны ответственности.

`environment=TEST` допускает только ответ с `test=true`; `PRODUCTION` — только `test=false`. HTTP всегда направлен на `https://api.yookassa.ru/v3`, Basic Auth, JSON, таймаут 15 секунд, перенаправления HTTP запрещены. Ошибки провайдера возвращаются как 502 без секретов и без автоматического создания другой транзакции.

## API для оформления заказа

Пути приведены относительно общего префикса `/api/v1`.

- `GET /payments/capabilities` → `{ provider: 'YOOKASSA', available, externalCallsEnabled, configured, environment: 'TEST' | 'PRODUCTION' | null, reason: string | null }`. Это только локальная проверка конфигурации, а не доказательство реальной доступности провайдера. В отключённом режиме `configured=false, environment=null`, поскольку секреты не загружаются. Интерфейс должен отключить оплату, если `available=false`, и показать `reason`.
- `POST /payments/orders/:orderNumber`, тело `{ returnUrl?: string }`. Защищён `OptionalJwtAuthGuard`: авторизованный покупатель передаёт Bearer JWT; гость — непрозрачный токен заказа в `x-order-access`. Перед любой работой вызывается `OrdersService.getAccessible(orderNumber, actor?: { sub: string; role?: string }, accessToken?: string)`.
- Ответ создания: `{ provider: 'YOOKASSA', paymentId: string, confirmationUrl: string | null, status: 'PENDING' | 'SUCCEEDED' | 'CANCELED' }`. Переход на оплату разрешён только при `PENDING` и непустой ссылке. После возвращения пользовательский URL не является доказательством оплаты: интерфейс запрашивает защищённый заказ.
- Сумма и валюта берутся из БД, никогда из тела запроса. RUB, положительная сумма, точная арифметика Decimal. Для действующего резерва нужны `priceSnapshot.deliveryConfirmed === true` и не истёкший `reservationExpiresAt`; старые WEB/B2B заказы без действующего резерва требуют проверки, а не молчаливой оплаты.
- `PUBLIC_APP_URL` должен быть абсолютным HTTPS-адресом без реквизитов, query и hash; HTTP допустим только для localhost/loopback. Адрес возврата создания платежа по умолчанию `/orders/:orderNumber`. Переданный адрес должен иметь тот же origin, без реквизитов и hash. Ссылка провайдера должна быть HTTPS в домене yoomoney.ru/yookassa.ru либо их поддомене.

## Идемпотентность создания

Короткая транзакция блокирует строку заказа PostgreSQL `FOR UPDATE`, проверяет оплачиваемый статус и находит существующий активный платёж (`CREATING`, `PENDING`, `SUCCEEDED`). Если его нет, создаёт `Payment` с `provider=YOOKASSA`, `status=CREATING`, `metadata={ idempotenceKey: UUID, returnUrl }`. HTTP выполняется вне транзакции.

Одновременные запросы используют один локальный платёж и один `Idempotence-Key`. В запрос ЮKassa передаются неизменные `amount`, `currency`, `capture=true`, `confirmation`, `description` и `metadata={ order_id, order_number, payment_id }`. После ответа сохраняется `transactionId`, а финансовая обработка делегируется атомарному hook заказа. Существующий `transactionId` проверяется GET, а не новым POST. Ошибка сети оставляет intent для безопасного повтора с тем же ключом и телом. Изменение суммы или старый `YOOKASSA_TEST` запрещают новую оплату и требуют проверки.

ЮKassa гарантирует идемпотентность только 24 часа. Неизвестный результат без provider ID старше 23 часов не повторяется: HTTP 409 и ручная сверка. Не удаляйте такой intent и не меняйте его ключ без проверки результата у провайдера. Административное разрешение повтора за пределами этого окна — отдельная задача.

## Восстановление пропущенных уведомлений

`PaymentsService` реализует `OnModuleInit/OnModuleDestroy`. Только при явном `STOREFRONT_EXTERNAL_CALLS_ENABLED=true` запускается интервал 60 секунд с `unref`; при завершении интервал удаляется. Перед каждой сверкой повторно проверяются флаг и `gateway.assertAvailable`. В отключённом режиме не читаются даже кандидаты БД.

За проход выбираются до 20 `YOOKASSA` платежей в `CREATING/PENDING` старше минуты. Внутренний cursor идёт по `(createdAt, id)` и после конца списка сбрасывается, чтобы старые неопределённые платежи не блокировали обработку следующих. Общий in-flight lock исключает наложение проходов. Promise-map по локальному payment ID объединяет одновременно выполняемые запросы провайдеру внутри одного процесса; между процессами финансовая идемпотентность обеспечивается сохранённым provider key и блокировками заказа.

Это внутренняя работа по записям БД, без публичного bypass авторизации и без HTTP endpoint восстановления. `transactionId` проверяется GET; при неизвестном ID повторяется тот же POST с исходным ключом/суммой/returnUrl (только в пределах безопасного окна). После проверки ID/суммы/валюты/metadata сохраняется ID и вызывается тот же атомарный `settleVerifiedPayment`. Ошибка провайдера/неопределённый результат не отменяет платёж и не освобождает резерв. OrdersService должен сохранять неопределённые резервы с активным `CREATING/PENDING` до подтверждённого исхода. Backend/timers не запускались для настоящих provider-вызовов при разработке.

## Уведомления

`POST /payments/webhook` принимает официальный формат:

```json
{
  "type": "notification",
  "event": "payment.succeeded",
  "object": { "id": "provider-payment-id", "status": "succeeded" }
}
```

Поддерживаются `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture`. Дополнительные поля официального объекта допустимы, но из объекта извлекается только валидированный ID. Старое тело `{ paymentId, orderNumber, status, idempotencyKey }` отклоняется.

Сначала находится локальная запись по `transactionId` и проверяется `provider=YOOKASSA`. Неизвестный ID возвращает 503 без обращения к ЮKassa: это также позволяет повторить раннее уведомление между HTTP-созданием и сохранением provider ID. Затем `getPayment(id)` получает актуальную серверную запись. Проверяются ID, точная сумма, валюта, `metadata.order_id`, `metadata.order_number`, `metadata.payment_id` и `paid=true` для успешного платежа. При несовпадении — 400 без изменения заказа. При ошибке GET — 502/503, уведомление не подтверждается.

Присланные event/status/amount/metadata не определяют финансовый результат. Актуальные `succeeded` → `SUCCEEDED`, `canceled` → `CANCELED`, `pending`/`waiting_for_capture` → `PENDING`. Захолдированные средства не считаются оплатой. После успешного атомарного hook endpoint отвечает HTTP 200; другие коды позволяют провайдеру повторить доставку.

## Hook родительского OrdersService

```ts
settleVerifiedPayment(
  paymentId: string, // provider ID = Payment.transactionId
  status: 'SUCCEEDED' | 'CANCELED' | 'PENDING',
  verifiedMetadata: {
    provider: 'YOOKASSA';
    orderId: string;
    localPaymentId: string;
    amount: string; // Decimal, два знака
    currency: string;
    providerStatus: string;
    paid: boolean;
    test: boolean;
    metadata: { order_id: string; order_number: string; payment_id: string };
  },
)
```

И при создании, и при webhook вызывается этот hook. Родитель отвечает за атомарность, необратимость финальных статусов, повторную сверку заказа под блокировкой, корректную позднюю оплату/отмену, складские резервы, бонусы, историю и очередь 1С. Повторный вызов не должен повторно начислять/списывать деньги, бонусы и остатки. PaymentsService не имеет собственных вызовов Loyalty/1C и не меняет финальные статусы самостоятельно. При сохранении metadata следует объединять данные, не теряя существующие служебные поля.

`PaymentsModule` импортирует `OrdersModule`, `AuthModule`, `SystemSettingsModule`; нужны экспорт `OrdersService` и экспорт/провайдер `OptionalJwtAuthGuard` в родительских модулях.

## Мок-проверки и будущая VPS-приёмка

### Подарочные сертификаты

`POST /orders/quote` и `/orders/checkout` принимают необязательный `giftCardCode` (общий строгий формат 32 hex-символа с дефисами). Для цифровой корзины адрес и способ доставки не нужны; Orders сохраняет `{ deliveryMethod: 'DIGITAL', email }` и снимки `OrderItem.productType/giftCardValidityDays`. Смешанные корзины запрещены. Покупка сертификатов не даёт бонусов и не оплачивается промокодом, бонусами или другим сертификатом.

Сертификат для физического заказа резервируется при checkout. Если денежный остаток положительный, ЮKassa получает **только остаток**; hold применяется атомарно с подтверждённым платежом. Начисления рассчитываются от денежного остатка минус доставка, не от суммы, покрытой сертификатом. При отмене неоплаченного заказа освобождается hold, но баланс не увеличивается.

При полном покрытии checkout сам атомарно применяет hold и создаёт `Payment { provider: 'GIFT_CARD', amount: 0, status: 'SUCCEEDED', transactionId: UUID, metadata: { redemptionId, giftCardAmount } }`. Нулевой amount — денежный остаток; фактически списанная сумма находится в реальной redemption-строке. Заказ становится `PAID`, физический резерв остаётся до отгрузки. Это не фиктивный ЮKassa-платёж: внешний gateway не вызывается и `POST /payments/orders/:number` для нулевого остатка возвращает 400. Интерфейсу не следует вызывать этот endpoint после уже оплаченного checkout.

После проверенной оплаты цифрового заказа сертификаты выпускаются в той же транзакции по неизменяемым снимкам, заказ становится `DELIVERED/CONSUMED`. Код доступен как `giftCards` только в авторизованном order GET владельца или гостя с действительным `x-order-access`; доступ staff к чужому заказу сам по себе кодов не раскрывает. Оба order GET имеют `Cache-Control: private, no-store`. В priceSnapshot, payment metadata и обычных публичных связях нет открытого кода, hash или encryptedCode. Возвраты уже потраченных сертификатов/оплаченных заказов автоматически не реализованы; фискализация для этих сценариев также требует отдельной реализации/приёмки.

Фискализация/чеки (54-ФЗ) **не реализованы** в этом gateway: POST `/payments` не передаёт `receipt`, позиции чека, ставки НДС или систему налогообложения; получение статуса чека также отсутствует. `SUCCEEDED` подтверждает платёж, но не выпуск фискального чека. `capabilities.available=true` означает только готовность конфигурации платежей, а не готовность фискализации. До включения реальных продаж необходимо отдельно реализовать/настроить выбранный способ фискализации и пройти его VPS-приёмку; до этого оставить внешние вызовы выключенными. Это документированный блокер запуска, а не автоматический программный контроль готовности чеков.

`npm test -- --runInBand yookassa.gateway.spec.ts payments.service.spec.ts`

Тесты подменяют весь HTTP и все операции БД. Проверяют выключенный режим, реквизиты/Basic Auth, официальный DTO, URL, ошибки и таймауты, неподтверждённую доставку, резерв, чужой доступ, единственный intent, неопределённый сетевой результат, поддельные/повторные webhook и проверку всех финансовых полей. Тест повторных webhook подтверждает отсутствие собственных финансовых действий PaymentsService и делегирование идемпотентному mock hook; настоящая атомарность OrdersService проверяется в его отдельных тестах.

До продаж на VPS отдельно проверить реальный тестовый магазин, оплату/отмену и дубликаты уведомлений, публичный HTTPS webhook/return URL, сценарий возврата браузера, фискализацию, поздний платёж, повтор после сбоя процесса, резерв и 1С. Возвраты денег, capture двухстадийных платежей и настройка подписки webhook не реализованы здесь. Реальные YooKassa/1С/СДЭК/Ozon-вызовы и локальные customer/order mutations в рамках этого блока не выполнялись.

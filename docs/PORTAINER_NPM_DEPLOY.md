# Установка SARKISIAN через Portainer и Nginx Proxy Manager

Этот вариант предназначен для **одного Docker Standalone на VPS**, где уже работают Portainer и Nginx Proxy Manager (NPM). Сайт, CRM, B2B и онлайн-запись используют один адрес `https://sarkisianbrand.com`. Существующий NPM продолжает занимать порты 80 и 443; стек SARKISIAN их не публикует. База, Redis, API и Nuxt не имеют опубликованных портов.

Схема: посетитель → HTTPS в NPM → внутренний `sarkisian-gateway:8080` → frontend или API. Для `/api/v1/` и `/socket.io/` gateway направляет запросы в API, остальные пути — во frontend. Health-проверки и API-документация через внешний адрес закрыты. Миграции выполняются отдельным сервисом до запуска API; первый администратор создаётся вручную после успешной миграции.

**Не включайте реальные обмены и платежи при первом тесте.** Принимающая доработка 1С и приёмка интеграций ещё нужны; без актуальных остатков 1С физические заказы сайта и B2B недоступны. Этот документ не означает, что VPS, домен или рабочие интеграции уже настроены.

## Перед установкой

1. Подтвердите, что Portainer управляет локальным Docker Standalone на том же VPS, где работает NPM. Для удалённого Docker environment Portainer не поддерживает сборку из Compose; в этом случае сначала нужны проверенные образы в registry, а эта схема требует отдельной подготовки образов. [Документация Portainer](https://docs.portainer.io/faqs/known-issues/docker-compose-files-including-build-steps-fail).
2. Убедитесь, что установлены актуальный Docker Compose v2 и версия Portainer, понимающая Compose-тег `!reset` и условие `service_completed_successfully`. При ошибке разбора не удаляйте зависимость миграций: сначала обновите окружение или согласуйте другой запуск.
3. В Git должна быть зафиксирована и доступна Portainer **проверенная версия** со всеми миграциями и двумя Compose-файлами. Текущая рабочая копия с незакоммиченными файлами сама на VPS не попадёт. Убедитесь, что в Git нет `.env`, паролей и локальных данных.
4. Для домена настройте DNS-запись на публичный IP VPS; для сертификата NPM должен быть доступен снаружи по 80/443. Если перед NPM стоит CDN или дополнительный proxy, представленные ниже правила IP к нему не применяются без отдельной настройки доверенных адресов.
5. В Portainer у администратора должен быть доступ к контейнерам, созданию сетей, логам и консоли. Потребуются свободные место и память для сборки четырёх образов. Ограничьте доступ к самому Portainer.

## Выделенная сеть для NPM

В Portainer → **Networks → Add network** создайте bridge-сеть `sarkisian-npm`. Включите возможность ручного подключения контейнеров; можно включить изоляцию сети. Через карточку работающего контейнера NPM подключите его к этой сети, **не отключая его прежние сети**. В эту сеть допускаются только NPM и gateway SARKISIAN; другие контейнеры не должны к ней подключаться, так как gateway доверяет адресу клиента, полученному от NPM. Эта сеть внешняя для стека: удаление/переустановка стека не должно удалять сеть NPM.

После настройки у NPM сохраняется прежний доступ к интернету и своим другим приложениям через его существующие сети. Содержимое и конфигурацию других proxy hosts не меняйте.

## Секреты и стек

На своём компьютере, в проверенной копии проекта, создайте новый файл настроек:

```powershell
node scripts/init-production-env.cjs sarkisianbrand.com admin@example.com
```

Замените email на свой адрес администратора сертификатов. Генератор создаёт независимые случайные секреты и не перезаписывает существующий файл. Откройте `.env.production` локально и добавьте строку `PORTAINER_PROXY_NETWORK=sarkisian-npm`. Секрет `INTEGRATION_ENCRYPTION_KEY` должен оставаться неизменным при последующих обновлениях: им шифруются настройки подключений. Храните все секреты и отдельный ключ резервной копии в защищённом хранилище. Файл с секретами не коммитьте и не присылайте в чат.

В Portainer → **Stacks → Add stack → Git repository**:

- имя стека — `sarkisian-crm-production`, совпадает с `COMPOSE_PROJECT_NAME`;
- укажите репозиторий и проверенный ref; для закрытого репозитория задайте Git-доступ в защищённых настройках Portainer;
- **Compose path:** `docker-compose.production.yml`;
- в **Additional paths** добавьте `docker-compose.portainer.yml` после основного файла;
- включите **Relative path volumes**, чтобы Portainer предоставил файл `deploy/postgres-init.sh`, нужный при первом создании базы;
- загрузите переменные из подготовленного `.env.production` через раздел Environment variables. Значение `PORTAINER_PROXY_NETWORK` должно точно совпадать с созданной сетью;
- автоматическое обновление из Git и profile `edge` не включайте. Значения автоматизации, почты, внешних вызовов магазина, WB-песочницы и индексации оставьте `false` на время изолированного теста.

Запустите **Deploy the stack**. Образы собираются из Git-копии; первый запуск может занять время. Проверьте, что PostgreSQL и Redis healthy, `migrations` завершился с кодом 0, затем backend и frontend healthy, gateway запущен. Сервис `migrations` должен завершиться — это нормально. При ошибке миграции API не должен стартовать; изучите журнал, не удаляя том базы и не создавая администратора повторно. По умолчанию Compose-профиль `edge` выключен, поэтому собственный Caddy не запускается.

Обновления делайте только с проверенного ref и с сохранением прежних секретов и томов. Поскольку Portainer при обновлении Git может заново клонировать директорию с bind-mounted файлами, используйте **Pull and redeploy / Re-pull image and redeploy** после принятого изменения и проверяйте, что контейнеры пересозданы с актуальными файлами. [Особенность Git bind mounts в Portainer](https://docs.portainer.io/faqs/troubleshooting/stacks-deployments-and-updates/empty-relative-bind-mounts).

## Первый администратор

После успешного старта откройте в Portainer **Containers → backend → Console** и подключитесь как текущий пользователь контейнера. Выполните:

```sh
node /app/scripts/bootstrap-admin.cjs
```

Введите одной строкой JSON с настоящим email и новым уникальным паролем, например `{"email":"admin@example.com","password":"ВАШ_ПАРОЛЬ"}`, затем нажмите Enter и Ctrl+D для окончания ввода. Используйте пароль 16–72 байта с буквами и цифрами. Он передаётся через stdin, а не как аргумент команды; не отправляйте его в чат и не сохраняйте в Git. Команда не меняет уже существующего администратора. При первом входе нужно сменить пароль. Удалите временный локальный файл с паролем, если создавали его для ввода.

## Настройка Proxy Host в NPM

Создайте **Proxy Host**:

- Domain Names: `sarkisianbrand.com`;
- Scheme: `http`;
- Forward Hostname/IP: `sarkisian-gateway`;
- Forward Port: `8080`;
- включите **Websockets Support**;
- запросите сертификат и включите **Force SSL**. Внешний HTTP допускается только для редиректа на HTTPS.

В **Advanced** для этого proxy host добавьте:

```nginx
set_real_ip_from 127.0.0.1;
real_ip_header X-Real-IP;
real_ip_recursive off;
client_max_body_size 85m;
proxy_read_timeout 120s;
```

Эти правила отменяют для данного host стандартное доверие NPM к входящим заголовкам из приватных Docker-сетей. NPM должен сам выставлять `X-Real-IP` из адреса подключившегося клиента, как в его стандартном `proxy.conf`; gateway принимает этот заголовок только потому, что его выделенная сеть доступна NPM и самому gateway. Не меняйте эту сеть на общую с недоверенными контейнерами и не добавляйте CDN/дополнительный proxy без согласования правил доверенных IP и сетевой фильтрации. Иначе IP и лимиты запросов могут работать неверно.

## Проверка после установки

1. Снаружи откройте `https://sarkisianbrand.com/`, `/crm/login` и `/b2b`; затем войдите под администратором и смените пароль. Проверьте публичную страницу и виджет тестового салона на HTTPS.
2. Из браузера открываются сайт/API без обращения к локальному IP; `/__health`, `/api/v1/health/ready`, `/docs` и `/docs-json` снаружи дают 404. Внутренние health checks контейнеров при этом остаются зелёными.
3. Проверьте рабочие уведомления/чат и WebSocket, загрузку файлов, выход и повторный вход. Проверьте, что 1С, SMS, почта, оплата и marketplace не выполняют реальные действия, пока их отдельно не настроили и не приняли.
4. Проверьте журнал gateway в Portainer: поле `client=` должно содержать настоящий адрес клиента, а не адрес NPM и не значение поддельных `X-Real-IP`/`X-Forwarded-For`, отправленных снаружи. Если адрес неверен, не включайте публичные формы и чувствительные операции до настройки доверенных proxy. Gateway не записывает query string в свой access log; отдельно проверьте правила логирования NPM и хранения его логов.
5. Создайте и проверьте резервную копию перед наполнением реальными данными, настройте расписание и отдельное хранение. Существующий `scripts/production-backup.cjs` требует доступа к Docker и Node на хосте и копии env-файла: **один Portainer UI пока не автоматизирует эту процедуру**. Нужен ответственный за выполнение/расписание и пробное восстановление; не считайте снимок VPS заменой проверенного согласованного backup. Порядок запуска, проверки и действия при аварийной остановке описаны в [инструкции по резервному копированию](PRODUCTION_BACKUP.md).

Откат образа возможен только при совместимой схеме БД. Перед обновлением сохраняйте проверенную копию и прежний ref; при несовместимой миграции восстановление выполняется в отдельное пустое окружение, а не поверх работающей базы.

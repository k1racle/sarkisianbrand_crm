# Изолированный контур прямых эфиров LMS

**Эфиры пока выключены на сервере независимо от настройки.** Этот файл и `docker-compose.lms-media.yml` — подготовка тестового контура, а не инструкция к включению платных трансляций. Сначала нужны защита активных участников при потере управления и полноценная приёмка; см. [LMS_LIVE.md](LMS_LIVE.md).

Для проверки предполагается отдельный адрес, например `wss://live.example.ru`, и отдельный экземпляр LiveKit для курсов. Клиент сначала получает временный токен через API своего курса. Nginx-шлюз `sarkisian-lms-gateway` отправляет каждый запрос и переподключение `/rtc`, `/rtc/v1` и соответствующие `validate` на проверку в backend; только положительный ответ пропускает соединение. Остальные пути, в том числе административный API LiveKit, через шлюз недоступны. Основной шлюз сайта не публикует внутренний endpoint проверки. Контрольный API LiveKit на порту 7880 не публикуется на хосте и доступен только контейнерам выделенной сети.

Токен LiveKit передаётся SDK в query string. Поэтому **журналы каждого внешнего прокси на пути к медиашлюзу, включая Nginx Proxy Manager, не должны записывать query string ни в access-, ни в error-log**. Подготовленный медиашлюз не ведёт такие журналы; это не меняет настройки NPM. Перед экспериментом администратор должен проверить фактическую конфигурацию NPM и отдельно убедиться с одноразовым тестовым токеном, что токен не появляется в его логах, системах мониторинга и сторонних прокси. До такой проверки не выдавайте реальные токены и не включайте трансляции.

## Сеть и отдельные ключи

Для отдельного тестового стенда и выделенного адреса добавьте Compose-файл `docker-compose.lms-media.yml` **после** основных файлов `docker-compose.production.yml` и `docker-compose.portainer.yml`. В защищённых переменных стека задаются:

- `LMS_LIVEKIT_URL` — точный публичный WSS origin медиашлюза без пути и query;
- `LMS_LIVEKIT_API_KEY` и `LMS_LIVEKIT_API_SECRET` — отдельная пара ключей LMS, созданная для этого экземпляра LiveKit;
- `LMS_LIVEKIT_GATEWAY_KEY` — независимый случайный ключ из 64 шестнадцатеричных символов. Он общий только для backend и медиашлюза и не должен совпадать с ключом LiveKit;
- `LMS_LIVE_ENABLED=false` до завершения всей приёмки. Самостоятельно снятие серверного предохранителя настройками недоступно.

В NPM нужен отдельный Proxy Host для медиадомена с доверенным HTTPS-сертификатом, WebSocket и направлением на `sarkisian-lms-gateway:8080` в существующей выделенной сети NPM. Убедитесь, что API LiveKit `7880` и внутренний endpoint авторизации недоступны снаружи и через основной домен. Не подключайте недоверенные контейнеры к сети медиасервера и не публикуйте его API для диагностики.

Подготовленный вариант использует `7881/tcp` и `7882/udp` для WebRTC; проверьте занятость портов, сетевые правила и реальный публичный адрес VPS. NPM проксирует HTTPS/WebSocket, но не заменяет эти медиапорты. Конфигурация **не настраивает TURN/TLS**: в сетях, где прямой UDP и TCP недоступны, соединение может не работать. Для таких случаев необходим отдельно проверенный TURN, сертификат, адрес и свободный порт; существующий NPM уже занимает 443 и его нельзя бездумно переназначать. Потребуются измерение нагрузки и ресурсов VPS, отдельное наблюдение и реагирование на отказ. Ориентиры: [порты LiveKit](https://docs.livekit.io/transport/self-hosting/ports-firewall/) и [развёртывание](https://docs.livekit.io/transport/self-hosting/deployment/).

## Что именно проверено

`scripts/lms-media-gateway-check.cjs` проверяет маршруты, отсутствие проброса клиентских заголовков, отказ при ошибке авторизации и отсутствие тестовых токенов в логах отдельного шлюза. `scripts/lms-livekit-protocol-check.cjs` создаёт временную изолированную Docker-сеть и проверяет настоящий WebSocket handshake LiveKit v1.13.11 с синтетическим токеном. Это не проверка реального VPS, NPM, межсетевого экрана, передачи видео, TURN или блокировки существующего UDP-соединения при падении backend.

`node scripts/lms-live-webrtc-check.cjs` и тот же запуск с `--partition` проверяют передачу синтетического видео и аудио между двумя Chromium через реальный LiveKit и gateway. Проверяются декодированные видеокадры и приём аудиопакетов, отключение участника через `RemoveParticipant`, отказ в повторном входе после имитированного отзыва, остановка медиасервера и прекращение передачи кадров при зависании тестового backend или разрыве его сети. Контроллер в этой проверке — заглушка, а не настоящий backend с базой прав; JWT и данные фиктивны. Тест использует временную Docker bridge-сеть и публикацию портов только на `127.0.0.1`, затем удаляет созданные ресурсы. Проверено локально на Windows / Docker Desktop; для CI и Linux необходим отдельный прогон.

До запуска нужны сквозные проверки с реальными браузерами и устройствами, контролируемый отказ backend и медиасервера, гарантированное закрытие активных соединений при потере контроля, проверка продления/отзыва допуска, отсутствия обходных маршрутов и восстановления. Также необходимы модерация, политика хранения чата и распределённый лимит частоты для нескольких экземпляров. Не подключайте рабочие ключи или клиентов до приёмки.

## Интеграционный тест управления на изолированном контуре

`backend/src/lms-live/lms-live-real-media-postgres.spec.ts` использует настоящие PostgreSQL, Nest-контроллер проверки допуска, сервисы управления и LiveKit. Он проверяет создание допуска, подписание и проверку токена, появление участника по signalling, отзыв доступа в базе и удаление участника при сверке, завершение сессии и закрытие комнаты. Только тест переопределяет серверную проверку готовности адаптера; production-код и его принудительная блокировка не меняются. Тест не проверяет пользовательский JWT guard, настоящий gateway/NPM или передачу видео: эти границы требуют отдельной сквозной проверки.

В PowerShell из корня проекта можно запустить тест на временных контейнерах, если порты `56438` и `56788` свободны:

```powershell
docker run -d --rm --name sarkisian-live-real-db-56438 -e POSTGRES_USER=lms_media_fixture -e POSTGRES_PASSWORD=lms_media_fixture_only -e POSTGRES_DB=lms_media_fixture -p 127.0.0.1:56438:5432 postgres:15-alpine
docker run -d --rm --name sarkisian-live-real-media-56788 -p 127.0.0.1:56788:7880 -e 'LIVEKIT_KEYS=fixture-key: fixture-only-livekit-secret-0123456789abcdef' livekit/livekit-server:v1.13.11@sha256:25cd902de7cacbd5f1f779f6a6ac1eae20ba8f56b0935934ce6b0ab80d1e3d20 --node-ip 127.0.0.1
Set-Location backend
$env:DATABASE_URL='postgresql://lms_media_fixture:lms_media_fixture_only@127.0.0.1:56438/lms_media_fixture?schema=public'
npx prisma migrate deploy
$env:LMS_REAL_MEDIA_TEST_DATABASE_URL=$env:DATABASE_URL
$env:LMS_REAL_MEDIA_TEST_API_URL='http://127.0.0.1:56788'
npm test -- --runInBand lms-live-real-media-postgres.spec.ts
Set-Location ..
docker stop sarkisian-live-real-media-56788 sarkisian-live-real-db-56438
```

Значения выше предназначены только для тестовых контейнеров. Дождитесь запуска PostgreSQL перед применением миграций; при сбое отдельно остановите только созданные этим тестом контейнеры. Тест откажется запускаться с другими адресами. В обычном прогоне Jest без этих переменных он пропускается.

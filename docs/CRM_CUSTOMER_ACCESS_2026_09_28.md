# BOX-01б3 — Customer 360: границы клиентов и организаций

Дата: 28.09.2026. Часть [плана коробочного выпуска](CRM_BOXED_RELEASE_PLAN_2026_09_24.md), не завершение всего Customer 360 или изоляции компании.

## Реализовано

- Контроллер Customer 360 передаёт текущего сотрудника во все операции. Списки, поиск, сводка, карточки, изменения, создание организации и добавление представителя проверяют серверную политику. GET-ответы приватные, без кэширования; идентификаторы и статусы валидируются.
- Старый GET `/crm/customers` использует тот же защищённый сервис. Ссылки на клиентов/организации в задачах и сделках фильтруются и проверяются при изменении; чужие записи и корзина не принимаются по прямому ID. Автопоиск клиента сделки также исключает корзину.
- У клиента появился явный `accountManagerId`, у клиента и организации — `createdById`. Автор задаётся сервером. Созданная из сделки карточка получает реального менеджера сделки/автора операции; новая организация по умолчанию — создателя.
- Записи из корзины не попадают в выдачу, поиск, сводку, связанные списки и карточки. Отсутствующий, чужой и удалённый ID дают одинаковый ответ, без раскрытия реквизитов.
- Чтение и изменение проверяются независимо. Переназначение проверяет доступность сотрудника и область получившейся записи; выход за разрешённую область откатывает транзакцию. Снять ответственного можно только с чтением/изменением всей базы.
- Изменения выполняются в serializable-транзакции, с блокировкой, согласованной с изменениями отделов. Конфликты сериализации и уникальных реквизитов возвращают понятный отказ, не содержимое чужой карточки. Аудит сохраняет автора, объект, действие и смену ответственного, но пока не полный diff всех полей.
- Представителем B2B может стать только активная внешняя учётная запись B2C/B2B. Внутренний сотрудник не превращается в покупателя через эту форму. Существующий клиент должен быть доступен для чтения и изменения. Создание клиента для внешнего пользователя без карточки требует доступа уровня компании. Повторная проверка роли при UPDATE предотвращает перезапись параллельного повышения пользователя в сотрудники.
- Связанные организации/представители, заказы, сделки, контакты, задачи, обращения и их счётчики фильтруются отдельно. Проекции не возвращают пароль, токены, внешние служебные metadata или весь объект пользователя.
- Интерфейс клиентов и организаций использует серверный `canWrite` каждой карточки: редактирование, архив и ПКМ не открываются только по общему `customers.write`. Общий компонент выбора ответственного использует серверный список доступных сотрудников. Отсутствие прав на историю заказов/обращений отличается от пустой истории.

## Области

Клиенты и организации используют разрешения `customers.read` и `customers.write`.

| Область | Какие записи входят |
| --- | --- |
| OWN | Ответственный — текущий сотрудник |
| PARTICIPATING | Ответственный или создатель — текущий сотрудник |
| DEPARTMENT | Ответственный находится в своём активном отделе |
| DEPARTMENT_TREE | Ответственный в своём отделе или его активных подразделениях |
| SELECTED_DEPARTMENTS | Ответственный в явно выбранных активных отделах |
| COMPANY | Все записи, кроме корзины |

PARTICIPATING здесь не означает отдельный настраиваемый список наблюдателей: такого списка у клиентов пока нет. Связь с заказом, сделкой или членством организации сама по себе не расширяет доступ к клиенту. Нераспределённые исторические записи остаются у пользователей с доступом компании; случайный отдел или автор им не назначаются.

## История и соседние области

- Сделки, взаимодействия по сделкам и задачи требуют своей области `crm.read`; карточка клиента не открывает всю CRM-историю. Взаимодействие без сделки доступно только при COMPANY `crm.read`.
- Пока нет полного единого scope-контракта OMS/Helpdesk, их история в Customer 360 доступна только при соответствующем **COMPANY** `oms.read` / `helpdesk.read`. Узкое или отсутствующее право закрывает этот блок. Заказ также не выдаётся через связь со скрытым клиентом/организацией.
- Сумма заказов сводки равна `null` без разрешённой истории OMS, не фиктивному нулю. Это ещё не полноценная финансовая сверка доходов/оплат/возвратов.
- Автоматическое сопоставление/создание клиента при сохранении сделки пока требует COMPANY-доступа к клиентской базе. При узких областях можно явно выбрать разрешённую карточку. Дедупликация/слияние — отдельный продуктовый пакет.

## Миграция

`20260928100000_customer_ownership`: три nullable-поля, внешние ключи `ON DELETE SET NULL`, индексы. Нет удаления, массового распределения клиентов, подстановки авторства или изменения ролей. Миграция применена только к проверенной локальной БД `localhost:5432/sarkisian_brand`; рабочий сервер не затрагивался.

## Открыто и следующий пакет

1. Рабочий источник прав по-прежнему сохраняет legacy COMPANY; профили **DRAFT_ONLY**. Поддержка областей проверена изолированными политиками, не означает их глобального включения для сотрудников.
2. Перед включением: конфигурация CRM, OMS/Helpdesk, экспорт, аналитика, уведомления и центральная корзина/восстановление должны получить и пройти свои серверные границы. Скрытая кнопка корзины не считается защитой API lifecycle.
3. Реестры клиентов/организаций всё ещё загружают список целиком; нужны серверная пагинация/лимиты, массовые операции с проверкой каждого объекта, импорт, дубли/слияние, версии редактирования и полноценная история. Связанные коллекции карточки ограничены 20–30 записями, отдельной пагинации истории пока нет.
4. Полевые права на коммерческие условия, независимые области организаций/контактов, участники-наблюдатели, безопасное массовое перераспределение и закрепление нераспределённой базы — отдельные обязательные задачи.
5. Следующий пакет **BOX-01б4 — конфигурация и оставшиеся межмодульные пути доступа**, затем контролируемая активация профилей с DENY. TIME/табель/Excel/кадровая 1С, VIDEO, заказы/финансы, CHAT, FEED, автоматизация и эксплуатация остаются в полной очереди, не заменены работой над правами.

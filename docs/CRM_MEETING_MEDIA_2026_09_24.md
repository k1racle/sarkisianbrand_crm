# VIDEO-01в — серверный медиадопуск и подготовка своего LiveKit

Дата: 24.09.2026. **Частичный этап, не работающая видеоконференция.** Владелец подтвердил `meet.sarkisianbrand.ru`; сервер — Ubuntu, 12 ГБ RAM, обычно 5, максимум 10 участников. DNS/сервер не изменялись. Интерфейс камеры, звука и экрана ещё не реализован; существующие страницы честно сохраняют `videoAvailable=false`, медиастатус — `clientAvailable=false`. Запись отсутствует.

## Что реализовано

- Аддитивные таблицы медиакомнат и медиасессий, привязанные к версии встречи. Применены только к localhost, без очистки/посева рабочих данных.
- Серверный адаптер LiveKit SDK `2.19.1`, зафиксированный в lockfile. Приватный RoomService только на loopback; WSS — отдельный публичный origin. Секреты только на сервере. По умолчанию **отключено**, локальный launcher принудительно оставляет оба флага `false`.
- Открытие организатором/уполномоченным администратором, выдача отдельного медиатокена сотруднику из состава встречи либо допущенному гостю. Право видеть компанию не даёт право незаметно подключаться к любой встрече.
- Комната до 10 участников; сотрудник/гость получает устойчивую непрозрачную identity своей медиасессии, не ID пользователя CRM. Имя отображается участникам. Нет прав администрирования, записи, создания/перечня комнат, изменения собственных metadata или отправки data-сообщений. TTL первичного JWT — 60 секунд; срок сессии дополнительно ограничен встречей/гостевым билетом.
- Повтор выдачи в действующей сессии не создаёт дубль. После отзыва/ротации билета новая identity не восстанавливает старую. Аудит первого открытия/выдачи и закрытия атомарен с записью БД; JWT/PIN/билеты/ключи не пишутся в аудит. POST-обновления токена не засоряют общий аудит.
- Отмена или **любое сохранение новой версии встречи** закрывает старые медиасессии в той же транзакции. Следующая версия может получить другую комнату. Перед подключением UI потребуется предупреждение о завершении текущего звонка при редактировании.
- Закрытие прежде всего запрещает новые подключения в БД. Ошибка удаления удалённой комнаты возвращает `disconnectPending=true`, не «все отключены». Периодическая сверка повторяет отключение, удаляет неизвестных и утративших права участников. При сбое сверки новые входы запрещены; успешная проверка не старше 15 секунд обязательна. Шаг между проходами — 3 секунды, не обещание фиксированной задержки при нагрузке.

## Почему нужен шлюз

В self-hosted режиме удаление участника не следует считать отзывом всех ранее подписанных JWT. Проверять надо и повторный вход/токены, обновлённые SDK, а не только первичную выдачу. Официальные [правила токенов LiveKit](https://docs.livekit.io/frontends/reference/tokens-grants/) описывают эти ограничения.

Архитектура пакета: браузер → `meet.sarkisianbrand.ru/rtc…` → Nginx `auth_request` → серверная проверка подписи **и актуальной БД** → локальный LiveKit. Проверяются активность сотрудника, текущие права/DENY, состав встречи, актуальный допуск/билет гостя, статус/версия комнаты и сроки. Отказ/ошибка не разрешают соединение. Семантика шлюза опирается на [модуль auth_request](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html).

`CRM_MEDIA_GATEWAY_ENFORCED=true` — лишь явное подтверждение оператором, **не автоматическое доказательство**, что обхода нет. Нельзя включать media до реальной проверки всех публичных маршрутов и закрытого порта 7880. Все `/rtc…`, включая reconnect/validate, должны проходить шлюз; `/twirp` и отладочные API наружу не публикуются. Авторизация не кешируется. JWT в query нельзя оставлять в access/error/CDN/APM-логах или аналитике. Шаблон удаляет альтернативный Authorization перед LiveKit, чтобы шлюз и медиасервер проверяли один query-токен.

**Важная граница:** шлюз проверяет установление соединения, не каждый медиапакет. Для уже подключённых участников отзыв выполняет серверная сверка. При недоступности БД/RPC действующее медиа может продолжаться до восстановления управления. До запуска необходимы отдельная проверка отказов, мониторинг и согласованный аварийный порядок остановки медиасервера; гарантированный мгновенный отзыв при сетевой изоляции здесь не заявляется. Это остаётся критерием эксплуатационной приёмки, не закрытым этим пакетом.

## API

Все пути ниже относительны `/api/v1`, ответы `private, no-store`.

| Путь | Метод | Назначение |
| --- | --- | --- |
| `/crm/meetings/:id/media` | GET | Состояние комнаты текущей версии, готовность сверки, ожидаемое отключение. CRM-права и область видимости обязательны. |
| `/crm/meetings/:id/media/open` | POST | `{version}` — версия встречи. Повтор открытия действующей версии идемпотентен; закрытую комнату не возобновляет. |
| `/crm/meetings/:id/media/close` | POST | `{version}` — версия медиакомнаты. Закрытие допуска доступно даже при отказе LiveKit. |
| `/crm/meetings/:id/media/token` | POST | Только текущая CRM-личность из сессии; организатор либо приглашённый сотрудник. |
| `/meeting-guests/media/token` | POST | `{ticket}` — отдельный билет допущенного гостя, не CRM-login. |
| `/meeting-media-gateway/authorize` | GET | Внутренний auth-request с двумя защищёнными заголовками, 204/401/403/503. Публичный API-прокси обязан скрывать этот путь. |

Rate limit: открытие 6/мин на сотрудника, токены 12/мин на сотрудника/гостя, публичная выдача 60/мин на сокетный адрес. Непроверенному X-Forwarded-For не доверяем. Перед запуском настроить доверенную прокси-цепочку/edge-limit: за одним reverse proxy сокетный лимит сейчас общий и может ограничить легитимных гостей. Одновременно контролируется не более 50 комнат; это защитный предел кода, **не нагрузочная гарантия** для 12 ГБ RAM.

## Конфигурация и запуск — ещё не выполнены

Шаблоны в [integrations/meetings](../integrations/meetings/). Это **не установщик**. Локально нет Docker/Nginx, поэтому их фактический запуск и `nginx -t` не проверены. В Compose выбран конкретный [LiveKit v1.13.7](https://github.com/livekit/livekit/releases/tag/v1.13.7), но совместимость с будущим браузерным SDK и реальной сетью нужно принять на staging. `restart: no`, отдельный профиль; ключи в YAML намеренно пустые. Никаких настоящих ключей в репозитории.

1. Уточнить версию Ubuntu, CPU, свободную RAM/диск, канал, существующие Nginx/контейнеры. Создать DNS `meet.sarkisianbrand.ru` и доверенный TLS по отдельному подключению к серверу. Текущий сайт не переустанавливать.
2. Подготовить отдельные сильные API/gateway секреты, заполнить приватный LiveKit YAML и backend environment по `integrations/meetings/backend-settings.example`. Ограничить чтение; не публиковать вывод конфигурации с ключами.
3. LiveKit API/signalling 7880 — только loopback, backend/gateway тоже недоступны напрямую извне. Для RTC отдельно проверить TCP 7881 и UDP 50000–50100, NAT/IPv6 и firewall. Диапазон — стартовый шаблон, не рассчитанная ёмкость. Настройки основаны на [портах LiveKit](https://docs.livekit.io/transport/self-hosting/ports-firewall/) и [развёртывании](https://docs.livekit.io/transport/self-hosting/deployment/).
4. Включить auth_request и приватный key-snippet, объединить `nginx-api-guard.example.conf` со **всеми** публичными API-vhost/алиасами. Не заменять существующий сайт примером конфигурации. Проверить `nginx -t`, logging/CDN, TLS и закрытые прямые порты до reload.
5. Выбрать TURN: отдельный домен/сертификат и доступный TLS/443. На одном IP с HTTPS нельзя просто занять тот же порт вторым процессом; нужен отдельный IP либо согласованная L4/SNI-маршрутизация. TURN в шаблоне выключен, полноценная связь в ограниченных сетях пока не обеспечена.
6. Только на staging после проверок включить два media-флага. До этого работать с обычным расписанием/гостевым залом ожидания, без ложной кнопки «Подключиться». Выключение флага прекращает выдачу/шлюз/сверку, но само по себе не останавливает уже идущие потоки LiveKit; для аварийного отключения нужен отдельный порядок остановки медиасервера.

# Календарь платежей CRM — FIN-01

Добавлен по запросу владельца 24.09.2026. Раздел **«Финансы → Календарь платежей»**, `/crm/payment-calendar`. Это планирование регулярных расходов и ручная фиксация оплаты, не банковская интеграция и не бухгалтерский регистр. Сайт, заказы покупателей и платёжные провайдеры не меняются.

## Первый рабочий объём

- Название, категория (связь, интернет, серверы, подписки, аренда, прочее), поставщик, сумма в рублях, первый платёж, примечание и видимость.
- Разово либо каждые N недель/месяцев/лет (1–36); квартал — 3 месяца. Окончание повторов необязательно, включительно. Для разового платежа интервал 1, окончания повторов нет.
- Представления «Месяц», «Список», «Планы». Клик по дню показывает платежи даты; поиск по названию/поставщику/категории и статусы. Реестр планов не ограничен выбранным месяцем, позволяет найти будущий или завершённый план.
- Итоги всего выбранного месяца: запланировано, оплачено, осталось и просрочено. Фильтры списка не меняют итоги — это явно подписано. Просрочка других месяцев не включается и не выдаётся за общую задолженность.
- Правая карточка, компактные действия 44 px, фильтры в одну строку на ПК, мобильная версия. Общие CSS-рецепты/токены «Моего дня», без оформления витрины и локальных SFC-стилей. Отдельная иконка календаря платежей, поиск/навигация из общего реестра.
- Отметка полной оплаты с фактической датой и комментарием. Исправление отметки требует причины, отдельного права и подтверждения. Никаких автоматических списаний, писем или кассовых операций.

## Правила данных

Денежные значения — целые копейки (без float в БД), от 0,01 до 10 000 000 ₽ на платёж. Валюта первого этапа — RUB. Даты без времени, просрочка рассчитывается по `Europe/Moscow`, а не по поясу БД/браузера. Дата оплаты не может быть в будущем, ранняя оплата будущего обязательства допустима.

Повторы вычисляются по первоначальной дате, без дрейфа: 31 января → 28/29 февраля → 31 марта. Для 29 февраля ежегодный платёж переходит на 28 февраля в обычные годы и возвращается на 29-е в високосные. Даты ограничены 2000–2100 годами. План сам не создаёт задания списания денег.

Оплаченная дата хранит снимок суммы, названия, поставщика и категории. Изменение плана пересчитывает **все неоплаченные даты**, включая прошлые; карточка предупреждает об этом. Для изменения тарифа только с будущего месяца следует ограничить старый план датой окончания и создать новый. После появления истории оплаты дата начала/частота/интервал закреплены, даже если отметка позднее исправлена. Уже оплаченные строки не исчезают при изменении даты окончания.

Создание и отметки защищены ключами повторного запроса, изменения — версиями. Одновременные правки не затираются молча; UI оставляет черновик при 409. Записи и аудит проходят в одной транзакции. Отмена отметки не удаляет след операции. Детали нового плана/состояния возвращаются без служебного ключа и хеша.

В первом этапе — до 500 планов во всей CRM. Лимит проверяется под блокировкой; никакого скрытого усечения сумм. Это ограниченный рабочий реестр для описанных регулярных расходов, не готовность к миллионам обязательств. Повторные отметки не создают дубли по плану/дате.

## Права и отделы

Отдельные операции: `payment_calendar.read`, `payment_calendar.write`, `payment_calendar.settle`. По умолчанию администратор получает все три, высшее руководство — только чтение; остальным новый финансовый доступ автоматически не выдаётся. Индивидуальные существующие DENY сохраняются. Новая безымянная роль «менеджер» не добавляется; назначение настраиваемых профилей по-прежнему требует завершения общей модели доступа.

Администраторы и высшее руководство с разрешением чтения видят все планы. У остальных авторизованных сотрудников: личные — только собственные, отдел — только текущий действующий отдел. После перевода/архива отдела прямой ID, список и итоги не открывают прежний отдел. Общие расходы компании может заводить/изменять высшее руководство лишь при отдельном праве изменения. Чтение само по себе не даёт права отмечать оплату. На каждом API-вызове активность, текущая роль, разрешения и область пересчитываются по БД, не по данным формы.

## Реализация и проверки

- `backend/src/payment-calendar/`; таблицы `CrmPaymentPlan`, `CrmPlannedPayment`; аддитивная миграция `20260924150000_crm_payment_calendar` — только localhost, без seed/reset и без изменений рабочих заказов.
- API `/api/v1/crm/payment-calendar`: GET месячного календаря, GET плана, POST создания, PATCH изменения, POST `/:id/settle`. Ответы `private, no-store`; DTO запрещают подмену владельца/отдела и лишние поля. В частности, строка `"false"` не превращается в положительную отметку оплаты.
- 18 unit-тестов: даты, високосные годы, 31-е число, интервалы, границы, копейки/DTO и московская полночь.
- `crm-payment-calendar-contract-check.cjs`: 39 HTTP-проверок с настоящими Nest/DTO/guard/service/PostgreSQL; синтетический только JWT-транспорт. Повторы, снимки, версии, идемпотентность, раздельные права, чужие отделы/перевод/блокировка/DENY, итоги без утечки и откат при ошибке аудита. Тестовые записи откатаны. Конкурентная нагрузочная проверка отдельных production-соединений не заявляется.
- Браузерная приёмка: `frontend/scripts/crm-payment-calendar-mock.cjs` — PASS на 390/1440 px после пересборки и перезапуска локального frontend. Проверены три представления, шрифты «Моего дня», правая карточка, кнопки 44 px, копейки, создание/изменение, конфликт 409 с сохранением черновика, отметка/исправление оплаты, чтение без изменения и восстановление после ошибки загрузки. Все бизнес-запросы перехвачены; реальные финансовые записи браузер не создавал.
- Регрессии `crm-ui-regressions.cjs` — PASS на 390/1440 px: таблицы, переключатели, вкладки и действия задач/сделок. `crm-navigation-mock.cjs` — PASS, 7 сценариев, включая скрытие финансового раздела/поиска и недопуск по прямому адресу без разрешения. Снимки календаря ПК/телефона просмотрены. Локальный маршрут отвечает 200, API без авторизации — 401. Production не менялся.

## Следующие расширения FIN-02..05

1. Напоминания ответственному до срока и при просрочке, уведомления «Моего дня», общий реестр задолженности за все периоды. Правила доставки/повторов, отказов и доступов — до включения рассылок.
2. Изменение тарифа «с даты», исключение/перенос одного повтора, отмена плана с историей, ответственный не только автор, организации/счета, лимиты и согласование расходов, частичные оплаты. Ничего из этого не имитируется первым интерфейсом.
3. Счета/чеки во вложениях, отдельное право выгрузки Excel, финансовый обмен/сверка с 1С. Не смешивать с кадровым табелем или автоматически отправлять расходы в endpoint заказов.
4. Банковские интеграции/подтверждение фактических операций, мультивалютность и прогноз кассовых разрывов — отдельное согласованное расширение, не текущая ручная отметка.

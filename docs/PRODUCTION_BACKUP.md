# Резервная копия и проверка восстановления

Эта процедура предназначена для администратора Docker-хоста. Нужны Node.js, доступ к Docker, проверенная копия репозитория той же версии, что установлена через Portainer, и защищённая копия переменных установленного стека. Portainer сам по себе запуск по расписанию не настраивает. До появления ответственного с доступом к хосту нельзя считать резервное копирование настроенным.

Копия включает PostgreSQL, снимок Redis, файлы загрузок, приватные файлы CRM и переданный файл переменных. Архив шифруется AES-256-GCM независимым 32-байтовым ключом. Храните ключ отдельно от копий и секретов стека; утраченный ключ восстановить нельзя. Сам зашифрованный архив также содержит чувствительные данные: ограничьте к нему доступ.

## Подготовка

1. Запланируйте короткое окно обслуживания. На время создания копии скрипт останавливает backend и после завершения снова запускает его, если он работал до начала. Сайт и API в этот период могут быть недоступны. Убедитесь, что миграции, обслуживание базы и другие процессы записи в БД или файловые тома не выполняются. Скрипт не управляет внешними приложениями и их записью.
2. Подготовьте на хосте файл переменных **этого установленного стека** в защищённом месте. Сохраните неизменными все исходные секреты, включая `INTEGRATION_ENCRYPTION_KEY`; без них зашифрованные настройки интеграций могут стать недоступны. Не сохраняйте файл в Git и не отправляйте его в чат.
3. Создайте независимый случайный ключ из 32 байтов в формате 64 шестнадцатеричных символов, например защищённым генератором паролей, и сохраните в защищённом хранилище. Не используйте для этого ключи JWT или интеграций.

## Создание и проверка

Команды выполняются в копии проекта на Linux-хосте. Пути и имя проекта в примере нужно заменить на свои. Не вставляйте ключ в командную строку или файл сценария: введите его без отображения, когда появится приглашение.

```bash
umask 077
read -r -s -p 'Ключ резервной копии: ' SARKISIAN_BACKUP_KEY; printf '\n'
export SARKISIAN_BACKUP_KEY
node scripts/production-backup.cjs backup /secure/sarkisian.env sarkisian-crm-production
```

Сохраните выведенный путь `Encrypted backup ready` и проверьте полученную копию, подставив этот путь:

```bash
node scripts/production-backup.cjs verify /path/to/production-backup-directory
unset SARKISIAN_BACKUP_KEY
```

Проверка расшифровывает архив во временный каталог, восстанавливает PostgreSQL в отдельный контейнер без сети, проверяет снимок Redis и извлекает оба файловых архива во временные контейнеры. Она не восстанавливает работающий стек и не проверяет доставку копии во внешнее хранилище. Скопируйте проверенную зашифрованную директорию в отдельное защищённое хранилище и отдельно убедитесь, что копия там читается и доступна при отказе VPS. Назначьте ответственного, расписание и контроль успешности выполнения; хранение только на том же VPS недостаточно.

Одновременные копии одного Compose-проекта запрещены: создаётся остановленный служебный Docker-контейнер с меткой `com.sarkisian.backup.project`. Он удаляется после завершения операции. Если процесс был принудительно остановлен или хост выключился, блокировка может остаться; не удаляйте её автоматически и не запускайте копирование повторно, пока администратор не убедился, что ни один процесс резервного копирования этого проекта больше не выполняется. После этого удалите именно оставшийся служебный контейнер через Portainer или Docker. Также проверьте состояние backend и временные каталоги `.staging-*` в `backups`: при аварийном завершении они могут содержать незашифрованные данные и требуют защищённого удаления администратором.

## Выгрузка для восстановления

На отдельной машине с Docker, достаточным свободным местом и тем же ключом выполните:

```bash
umask 077
read -r -s -p 'Ключ резервной копии: ' SARKISIAN_BACKUP_KEY; printf '\n'
export SARKISIAN_BACKUP_KEY
node scripts/production-backup.cjs unpack /path/to/production-backup-directory
unset SARKISIAN_BACKUP_KEY
```

Команда сначала повторяет изолированную проверку, затем создаёт новую директорию `backups/recovery-*` с расшифрованными файлами; существующие данные она не перезаписывает. В ней есть секреты и личные данные — обеспечьте доступ только администратору и удалите её безопасным способом после использования. Для полного восстановления требуется отдельное пустое окружение, совместимая версия приложения и сохранённые секреты; применение файлов и запуск восстановленного приложения должны быть проверены отдельно. Успех `verify` или `unpack` не означает, что реальное восстановление на VPS уже выполнено.
